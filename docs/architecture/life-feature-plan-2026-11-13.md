# Shadow Life 功能优化与实现方案

2026-11-13 · 已实现 20 项功能，真机验收与真实样本覆盖见下文 · 调研时的源码基线 `main@e835c65`。合并两轮调研的 20 项建议。优先级按日常使用机会、现有数据能否支撑、交付后能否独立使用排列。频率与收益是产品判断，尚无个人使用统计或真机耗时基线。

### 合成样本验收

- 303 条训练中有 300 条无关历史。旧的逐页再读详情用了 308 次服务调用，新查询 1 次取回最近三次。一次本机 PostgreSQL 测得 200 毫秒和 1 毫秒，未计网络往返。
- 七条购买明细中六条起初可比较。为双瓶装补规格后可换算第七条。未分配的退款仍标出；完整分配的退款按购买行计算。两个售后事项同时申领同一笔退款时只有一个分配成功。
- 门店检索兼容旧版继续写入的「门店｜菜名」和已有出处。并发收录保留原食品编号，同名分店分别保存；当餐估重保存在摄入条目。真实食堂和账单均未用于写入测试。
- 采集线索提供已关联正式账的发生日期和状态。期间核对以正式账发生日合计，候选双方保留原始时间、渠道与凭据。缺时刻的同日同额记录保留在合计中，用户可核对详情。
- 回归涵盖移动父容器及循环、检验定性结果、跨午夜发作、12 秒选段、撤销录音后的文字回看、缩短手工区间和两段重叠。浏览器实际执行了半小时散步补记和生成容器二维码。
- Android 已验证 Kotlin 编译与单测。新版本真机触摸、飞行模式冷启动和个人真实订单的可比覆盖率仍待发布前核验。

## P0 实现拆解

### 01 在昨晚睡眠下记晨起感受

**操作。** Android 健康 → 睡眠，在所选醒来日填精力、睡眠质量或一句话；Web 健康日详情可查看、补记和更正。近 14 个醒来日并列主睡眠时长和晨评，点一行回到当天。没有设备记录也能留下晨评。

**数据与执行。** 已有 `daily_wellbeing` 的精力、睡眠质量和备注，以及按醒来日选主睡眠的规则。现有 wellbeing 接收路径属于原始数据摄入。建议新增用户命令 `health.save_morning_checkin`，沿用健康写权限，服务端生成稳定手工来源身份，经既有 wellbeing 归一化与投影保存。为该来源补充仅由服务端创建的类型、数据库约束与查询映射；设备同步游标仍只管理原有来源。手工来源以账号、醒来日和所选时区唯一，保留首次填写时刻、所指醒来日和修订。旧的日感受按原来源显示；晨评只改自己创建的手工行。返回精力等所需字段即可。14 天对照采用仅需健康读权限的范围查询，无需饮食读权限。[健康载荷与日汇总](../../shared/contracts/src/schemas.ts) · [归一化实现](../../server/database/src/health-normalizer.ts) · [主睡眠选择口径](wellness-review.md)

**验收。** 用跨午夜睡眠、午睡、迟到的设备记录、仅晨评和补填昨天五组数据。两端对同一醒来日看到相同配对；睡眠重同步后晨评仍在，旧来源可查。两端同时首次填写遇唯一键竞争时返回已有记录与修订，让用户保留输入继续更正。Android 断网重试只产生一条手工记录。

### 02 训练中途换动作，并直接读取最近三次表现

**操作。** 当前动作提供「换动作」。已完成两组则保留两组，未完成的剩余位置切换到所选动作，输入按新动作的次数或秒数、器械和重量重新开始。换到已在组合中的动作时定位现有动作并追加空组，遵守每动作组数上限。用户点「以后也这样练」才单独更新计划，训练保存与计划更新分别返回回执。

**实现分两次合并。** 先加有界只读查询（拟用 `health.exercise_history`），按主体、动作 ID、单位、器械读取最近三个有有效完成组的训练，日期及稳定 ID 排序，返回记录 ID 与实际组。当前 Web 实现会逐页找训练并逐条读详情；两端改为每次选动作最多一个历史请求。先对已有力量训练 JSON 做有界返回并测查询计划、耗时；只有数据量证明需要时才加投影或索引。再改两端草稿与进行中控件，沿用 `health.record_workout` 和 v1 的唯一动作约束，历史草稿继续可恢复；编辑长期计划走原 `health.set_plan` 的修订检查。[Web 历史查询](../../client/web/src/workout-history.ts) · [组与草稿](../../client/web/src/workout-session.ts) · [Android 草稿](../../client/android/app/src/main/java/com/shadow/life/TrainingDraft.kt) · [实际动作合同](../../shared/contracts/src/workout-menu.ts)

**验收。** A 已完成两组后换 B 完成一组，保存和断线重试后仍只有 A×2、B×1。覆盖换回 A、次数换秒数、无历史、历史记录作废、切换动作时旧响应晚到、恢复 v1 草稿，以及计划更新失败后训练仍可查看。以同一批有大量无关历史的合成数据记录改造前后请求数与耗时，再决定索引策略。

### 03 在当日行程中看到赶车余量

**操作。** 在离开地点和下个固定时刻之间显示「交通约 45 分钟 · 提前到站 25 分钟 · 可机动 20 分钟」。点开可改预计离开时刻、交通方式、交通耗时与提前量。第一版接受手填，保留估算来源。固定时刻取选中的有效预订或日程点。

**数据与计算。** 现有日计划停留点有稳定 ID 和可选开始时间，预订另有状态、可见范围和起止时刻。建议把衔接保存为有版本的计划附属记录，关联日计划、起点停留 ID、终点停留或预订 ID，读时基于当前版本计算。衔接变更校验计划修订；移动停留顺序后检查相邻关系，删除端点后提示重选。用明确时区解析为时刻，按分钟计算「目标时刻 − 离开时刻 − 交通耗时 − 提前量」。地图已有驾车行程只在方式、端点吻合时作为可选估计。Web 当日行程、Android 和离线 HTML 共用同一计算结果与样例；私密预订及可反推其时刻的余量只输出给有权查看者。现有 v1 Bundle 继续可读写；需要携带衔接往返恢复时增加可区分的新版导出，保留原导入器。[日计划与预订合同](../../shared/contracts/src/schemas.ts) · [地图与备选点规则](../execution/google-travel-map-2026-09-24.md) · [按日与离线行程](../execution/travel-reservations-2026-10-28.md)

**验收。** 16:30 离开、18:00 发车、交通 45 分钟、提前 25 分钟，结果为 +20 分钟；改为 17:00 离开，结果为 −10 分钟。另测跨午夜、夏令时、取消或改签、只有出发日期、手动设提前量为零、缺交通时间、成员仅能看公开预订。离线显示生成时刻和当时估算。

### 04 从店铺查下次想点什么

**操作。** 在已确认的购买明细行旁点「还会点／避开」，可记「微辣」；店铺页按明确偏好展示最近一次评价，也允许手记「下次想试」。Android 从消费详情进入，Web 支持按店整理。第一版保留原订单整单评分和复购意愿，店铺页可单独显示最近整单备注。

**数据与执行。** Web 已有整单体验表单，直接调用 `life.correct_purchase`。新增菜品偏好对象，包含主体、门店身份、菜品名、用户选择、备注、可选购买行引用与修订。优先采用明确门店或用户确认的别名；只有商家文字时按来源与可辨认门店分组，同名连锁分店可由用户选择归属。首版允许从确认的商品行带入或手动添加。只有截图、折叠摘要或加料行时可先记店铺笔记；菜品身份清楚后再关联。一次点选直接保存，不产生餐次、付款或整单修订。[既有体验表单](../../client/web/src/PurchaseExperiencePanel.tsx) · [商家别名与明细范围](consumption-statistics.md) · [消费与餐次关系](consumption-bill-chain.md)

**验收。** 两家同名分店、同单多人点餐、同菜不同做法、点过但没评价、想试但没买五种情况都能区分。清除偏好后历史订单和整单评分仍能读取；重新识别同张截图不会复制偏好。

### 05 随时查「上次是什么时候」

**操作。** 新建「换滤芯」后点一次「今天做了」，随时查看上次日期、距今天数及最近几次间隔。能补填旧日期、改错或撤销。理发等已有次卡记录的事项，可从某次核销或物品维护详情关联。

**数据与执行。** 建事件定义与发生记录。定义存名称和归档状态；发生记录存本地日期、时区、可选时刻、备注及可选来源类型与 ID。直接记录和引用既有事实共用一个列表。对同一定义与同一来源设唯一键；手动发生使用稳定命令 ID，允许一天内真的发生两次。源事实更正、撤销或失去读取权限后，按当前有权读取的有效来源重算；跨域结果只显示有权使用的记录。第一版按本地日历日计算间隔，详情可见两次的原始日期。Android 快速新增、Web 历史列表、CLI 的创建／记录／查询走同一业务能力。[次卡核销的修订与撤销](service-cards.md) · [既有操作与读取边界](../../ARCHITECTURE.md)

**验收。** 只有一条时显示上次日期；两条后出现间隔；倒序补填中间日期后相邻两段同时更新。检查同日两次、重复提交、关联已核销记录、核销撤销、跨账号读取。无需先建周期计划。

## 合并、兼容与验证

1. 每个编号各有可见入口、读写合同和独立回归。新能力名均为建议名，实施时在 `shared/contracts/src` 注册。普通写操作沿用 Executor、稳定命令 ID、修订冲突和操作回执；读取走既有 QueryService、主体权限与分页。Agent 经 life-operator 的 CLI/API 使用同一语义。能力发现按执行权限过滤，客户端依据实际支持的能力显示入口。[项目架构](../../ARCHITECTURE.md) · [Agent 接入](../agents/integration.md)
2. 先交付兼容旧资料的读写与可选字段，再接 Web 与 Android。对于严格校验的旧响应或旧 Bundle，用单独的新查询或明确区分的格式；新增关联可以为空，旧原图、历史日计划和训练草稿各取一份样例回归。同一事实的原始日期、时区、精度和来源都保留。新表按主体与来源建约束，新命令测试双端并发、冲突回读和队列重放。
3. 改公共合同时执行 `pnpm --filter @shadow/contracts generate`、`pnpm check` 和 `pnpm test:full:offline`。改 Web 加生产构建和相关浏览器流程；改 Android 跑 Kotlin 编译、单测，涉及触摸和断网恢复的场景另记真机结果。01、02 分别扩展 `pnpm test:wellness:offline`、`pnpm test:workout:offline`，03 扩展[离线行程流程](../../scripts/test-travel-reservations-offline.mjs)，04、05 在消费与日常工作流中覆盖上文样例。
4. 每项合并时记录使用的样本、可复现操作、实际结果和仍缺的真机证据。查价覆盖、图像定位成功率及训练历史耗时需记录分母或数据规模。本文中的数值例子和准入线都是设计用例；真实覆盖与性能待实施测量。
