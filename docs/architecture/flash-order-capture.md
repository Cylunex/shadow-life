# 淘宝闪购长订单采集与付款材料归组

## 范围与现状

以两种外卖订单布局为依据，设计淘宝闪购（原饿了么）的长页采集。本文不保存用户原图、真实店名、订单号、地址、电话、骑手或支付账号。

当前源码优先读取美团订单的无障碍文字，微信／支付宝保留原有单笔支付账单读取。没有正文节点的来源应用保存长截图或直接分享系统长图，交给所选 LLM 或 Losna；移除 Android ML Kit OCR，订单图片不会自动调用服务端 Tesseract。

无障碍读取、可控逐屏采集及识图路径的最新范围见[2026-11-09 交付说明](../execution/order-capture-native-and-llm-2026-11-09.md)。历史 OCR 原材料保持原样，不通过本轮源码更新批量修正或补记。

## 订单字段与区域

按顺序读取四个区域：店铺和配送状态、商品行及费用、价格明细、订单信息。遇到“安心权益”“常见问题”即结束，不采推荐商品。收货信息、备注、发票和配送骑手不进入商品或支付字段。

脱敏验收样例：

| 项目 | 订单 A：粉面及配料 | 订单 B：套餐及小料 |
| --- | --- | --- |
| 商品/选项行数 | 8 | 5 |
| 商品行实付合计 | 17.98 | 21.76 |
| 打包费 | 2.00 | 1.50 |
| 配送费实付 | 0.00 | 0.00 |
| 总价 | 46.48 | 50.74 |
| 优惠合计 | 26.50 | 27.48 |
| 订单实付 | 19.98 | 23.26 |

金额统一用十进制定点计算，分别校验“商品行实付 + 打包费 + 配送费 = 订单实付”和“总价 - 优惠合计 = 订单实付”。不把划线原价、配送费原价或任一商品的“实付”当订单总额。已摊入商品行的优惠不能再次扣减。

“特辣”“不要保温袋”作为零元订单选项保存，不自动创建食材或摄入记录。商品 OCR 名称（含读到的规格文字）、数量、行实付和选项标记分别保存；商品原价不进入已确认的结构化字段，仍可查看原图；营养和实际吃了多少保持未知。

“订单已送到指定位置”是履约状态。“尽快送达”是配送要求，不是送达时刻。下单时间（可能带毫秒）单独保留，不作为付款时间。支付方式“支付宝”不等于支付宝交易号。

## 长页采集流程

1. 显式摇动后固定账号、来源应用和窗口，校验解锁及对应开关。美团可读订单以节点文字、原始位置及重复行创建 `life.takeout.v1` 观察，通过 `life.ingest_activity` 保存，不附加图片或消费写入意图。订单号码支持空格分组，元数据可位于商品费用之前。
2. 图片路径自动滚动，用户可手动慢滑、恢复自动或直接完成。停滞后转为手动。只有点击完成才保存。美团原生文字继续逐屏读取。
3. 图片以正文多区域验证重叠。对齐不可靠处保留两侧视口并开始新段。编码时按段解码，超出上传限制时按视口边界再拆段。美团文字按正文锚点对齐，解析在合计后截断推荐材料。
4. 图像采集上限为 32 屏及 32 MB 压缩帧，文字上限为 12 屏，会话最长 5 分钟。每段图像最多 18000 像素高、2400 万像素及 10 MB。切换来源窗口、锁屏、账号切换或关闭功能时终止。图片进入加密附件队列，按段序及同批次提交。
5. `life.capture_screenshot.recognition` 为 `losna`（默认）、`llm` 或 `save`。仅 Losna 路径带 `losna:process`；分享批次保留 `losna:batch`。LLM 路径使用服务端允许的 `vision_model_id`，排入 `llm-vision-v1:<id>`，Worker 领取同一 Executor 租约并保留模型来源。仅保存不触发处理。不存在的模型／暂停／预算不足均保留原图，不自动切换识别方式。
6. `life.capture_workspace.screenshot_models` 只暴露配置好的远端视觉模型 ID 和名称。服务端沿用 `SHADOW_LIBRARY_PROCESSOR_CONFIG_FILE` JSON 与 `shadow.library.vision.request/response` 视觉协议，模型路由、URL 和凭据不由手机提供；现有通用资料处理仍兼容旧处理器。模型返回受合同校验的资料候选，不直接创建付款事实。

美团商品价格可能尚未摊入红包。可以核对商品标价、实际配送费与红包后的订单合计，但未明确分摊的逐项实付仍为空。带划线原价／优惠价的配送行只采用最右侧最终价格，无法确认或还有未知收费时不宣称核对一致。

## 三种身份及去重

- 订单平台身份：平台 + 平台账号 + 外卖订单号。
- 付款身份：支付平台 + 支付账号 + 支付交易号。
- 采集身份：设备 + 来源 ID，重试沿用同一个命令 ID。

支付宝账单中的订单号可能是支付交易号，商家订单号也可能与闪购前台订单号不同。只有来源明确提供两端身份的桥接证据，才能持久关联两个平台的事实。不同外部编号不得硬替换；金额和店名相同不作为强身份。

外卖观察始终不自动增加支出，也不自动写入餐次或购买事实。完整且金额核对一致、无问题的观察，仅在店名、实付、支付方式、时区和下单后 0–120 秒付款窗口唯一对应时返回只读 `related_record_id`；店名 OCR 不一致、退款、冲突、歧义或缺少权限均不归组。Android 订单列表按对应消费合并展示材料，原始身份保留。

## 重复外卖观察与首页文字

同一外卖订单的多次观察选择一份完整、金额核对更好的快照，质量相同时选择后一次；不跨截图累加商品行或拼接金额。商品和店名的文字差异不单独触发冲突；订单号、实付、总价、下单时间或支付方式不同仍提示冲突，取消与退款观察优先保留警示。

`life.activity_source.capture_order_id` 返回来源所属的订单 ID。首页将外卖截图命令接入最近文字采集，按这个 ID 合并显示，并隐藏已由文字入口代表的原图卡片。来源和原图不删除，材料数仅计当前本机最近队列中的来源。无法确认订单 ID 的材料保持独立，不能仅凭同价或相近采集时间合并。

## 无交易号支付成功页的展示归组（已实现）

成功页可能只有“支付成功”、金额和付款方式，账单详情才有交易号与付款时刻。前者继续保留为原始材料，后者按既有交易身份入账。

`life.activity_source` 新增可选 `related_consumption_record_id`，与真实来源关联 `consumption_record_id` 分开：

- 仅处理带持久化付款采集上下文、无订单号/交易号的成功页。
- 平台、平台账号、设备、时区、人民币实付和明确付款方式必须一致。
- 对比成功页的采集时刻与账单明确付款时刻，要求成功页在付款后 0–15 秒内出现；账单采集可能晚得多，不拿后一次摇动时刻做匹配。
- 仅在当前可见、已确认消费中存在唯一对应记录时返回；退款、冲突、不同账号、无付款方式、超时或候选过多均不归组。所有查询按所有者隔离，缺少金额读取权限不返回关系。
- 每次读取重新计算，后来出现相同时间/金额的竞争记录时撤回；不写入交易身份，不改变金额，不删除材料，不用于触发入账。

Android 首页按真实消费 ID 归组，优先显示已入账账单结果，合并多份本机采集材料的计数。原始材料列表仍保存每次采集，便于回溯。这个计数不是该消费全历史来源总数。

## 验收重点

两个不同金额的成功页与两张后补账单显示为两条消费；重复读取不产生写操作。反向上传、跨午夜、不同账号/设备、同金额近时竞争交易、删除来源、作废消费、缺少权限和旧版本客户端均需覆盖。长页部分用脱敏商品布局、隔离数据库和原图离线 OCR 验证金额核对、重复观察、停止区域与来源保留；真实应用手势未视为已验收。
