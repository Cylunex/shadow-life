# Life 事件记录与分类详情设计

状态：2026-10-31 设计基线；已交付行为与验证见[交付记录](../execution/event-details-2026-10-31.md)。本轮覆盖 Android 主客户端与 Web 同源展示，不调整 Losna 工作流。

Life 的阅读单位改为一次生活事件：一次称重、一顿饭、一晚睡眠、一次训练、一笔消费。详情根据内容选择结构，采用纯黑暗色背景与明亮领域色，浅色模式采用奶油白。后台原始数据和指标继续完整保存，处理结果仍按既定路径由 Losna 的 QQ 通道通知。

本方案更新[整体体验设计](android-experience-design.md)中的雾蓝视觉方向和通用详情布局，保留四个主页面、首页自定义排序、离线队列、返回路径及阅读连续性。

## 当前问题与证据

| 位置 | 当前行为 | 设计后行为 |
| --- | --- | --- |
| Android `LifeScreens.kt` 的 `DetailScreen` | 类型决定头部图标与主数字，主体仍循环 `DetailSectionContent` 输出事实字段和分组 | 公共外壳只处理加载、返回和操作；内容由有类型的详情组件呈现 |
| Android `NativeLifeRepository.kt` | 多数领域数据提前变成字符串 `DetailFact`，时间序列、单位和来源语义不便继续用于图表 | 保留原始数值、单位、时间精度、覆盖情况和来源类型的展示模型 |
| Web `RecordDetailContent.tsx` | 主体 `DetailValue` 递归展示对象和数组 | 同一套领域语义，按类型布局；未知类型才使用明确标签的简洁后备页 |
| `ScaleScanService.kt` | 一次稳定读数已包含体重、阻抗、可选心率和多项推导体成分，作为一个 body 原始记录上传 | 沿用采集方式，不把显示问题当作采集重复删除 |
| `health-normalizer.ts` | 将同一原始记录投影成多条 observation，保留共同 `group_id`、`raw_id` 与版本 | 指标继续用于趋势、分析和修订，列表按事件组合 |
| `postgres.ts` 的 `lifeTimeline` | 对 observation 逐行返回；标题可能是 `original_field` | 一次称重一张卡，标题为“身体测量”，设备退到来源行 |
| `lifeSearch` | 当前健康分支主要检索手动 measurement，未覆盖同等范围的设备 observation | 搜索子指标，返回父事件并高亮匹配指标 |
| `LifeTheme.kt` | 多层中性灰、雾蓝；未选择外观的账号默认深色 | 保留深色默认与已有外观选择，暗色背景改为纯黑，领域色承载视觉重心 |

这些结论来自当前源码；未查询生产数据。旧迁移记录是否存在不同 raw 之间的真实重复，在实施时另做只读核查，不能仅凭“同一分钟、同样体重”合并。

## 记录页按事件组织

顶部保留搜索、日期和领域筛选。默认“生活事件”，增加可切换的“全部数据”用于查看底层指标与采集材料。按天分组、按真实发生时间排序；只有日期的事实显示在该日“时间未记录”区域，不生成 00:00。

每个事件行显示时间、内容标题、一个主值与最多两项辅助值。图片、阶段条、路线和食物清单只在对应内容中使用。来源用次级文字，内部字段名和原始同步编号不进入标题。健康高频采样、应用使用与后台材料默认按实际会话或当天摘要呈现，不挤占日常事件流。

示例：一次含 16 个指标的称重，在事件页显示“身体测量 · 68.4 kg · 体脂 21.8% · 小米体脂秤”。进入后看到全部 16 项。记录数分别称为“1 次测量”和“16 项指标”，不能混用。示例数值仅用于设计。

| 数据 | 默认事件单位 | 展开后 |
| --- | --- | --- |
| 体脂秤、血压、化验 | 同一明确来源批次或会话 | 同批指标、原始／推导标记、逐项趋势 |
| 睡眠 | 一次睡眠会话，日期沿用起床日语义 | 分期、开始结束、主睡眠／其他睡眠 |
| 运动 | 一次运动或训练会话 | 路线、分段、动作和完成组 |
| 全天活动及连续采样 | 当日已有权威汇总，或确定的采样会话 | 步数、时长及相应明细；缺汇总时不拼造总量 |
| 饮食 | 一餐，内部多种食物 | 食物份量、已知营养、相关账目 |
| 消费 | 一笔交易或已有购买记录 | 商品、付款、退款与凭证关系；不把相似商户自动合并 |
| 分享资料 | 明确分享批次可作为一组入口 | 每张图／每份文件仍能单独打开和更正 |
| 录音、应用使用、地点 | 一次录音、使用区间或停留 | 原音、转写、时间段、位置证据 |
| 物品与计划 | 已完成的维护或行动事件 | 打开物品档案或对应项目；未完成计划留在计划页 |

### 称重分组规则

1. 以主体权限过滤后的 `group_id` 作为主分组证据，同时验证 `raw_id` 一致。仅收录有效投影，同组必须对应同一有效原始版本；新版本尚未完整投影时保留最后可读完整版本或明确处理中。
2. 不按显示日期、相近时间、体重或设备名字猜测批次；不同来源、不同用户、不同会话分别保留。历史缺少批次证据时保持独立记录。
3. 服务端在分页和计数之前分组。稳定事件 ID 由来源对象导出，不依赖首个指标 ID；排序键使用事件时间与稳定 ID，补齐指标不会产生新事件。
4. 同步重试、迟到阻抗、体成分补齐更新原事件。删除或更正子指标后重新计算摘要，整组无有效指标才移出列表。
5. 指标趋势和 Agent 的事实对象 ID 不变。旧 observation 深链仍可打开，展示所属测量并定位该指标；未知父级时回落到单指标详情。
6. 全部数据视图保留每个指标。搜索按子项匹配、按事件返回，并包含匹配子项，搜“肌肉量”不要求用户先知道称重时间。

事件摘要应批量查询，列表不得逐卡调用完整详情。若一组有大量样本，返回摘要、样本数及独立明细游标，避免把原始数组塞进首页。

## 分类详情布局

每个详情首屏回答“发生了什么、主要结果、什么时候”，第二屏呈现内容结构，再显示关系与历史。来源、同步、原始数据和修订放在页尾可展开区域。真实缺项用“未记录／来源未提供”，失败给局部重试，不能用 0 填空。

| 类型 | 首屏主内容 | 专属结构与主要操作 |
| --- | --- | --- |
| 身体测量 | 大号体重、测量时间；有可比历史时显示变化及基准日期 | 体脂／肌肉／水分等分组指标网格；切换指标看趋势；每项标明设备值或计算值；查看同次全部指标 |
| 血压及其他单项测量 | 血压上下值成对展示，或单指标值与单位 | 同次脉搏、测量条件和历史；缺少配对字段时不强造一对；手动数据允许原有更正 |
| 化验与体测 | 项目名称、报告日期与原件入口 | 按原报告分组；每项结果、单位及来源提供的适用范围；未提供范围不自行判正常 |
| 睡眠 | 总时长与起止时间 | 有真实时序时画睡眠阶段时间轴；只有阶段总量时画构成条；主睡眠与补觉分列，未知阶段留空白标记 |
| 跑步骑行及步行 | 距离、时长与适用的配速／速度 | 有真实路线才显示地图；有序列才显示心率和分段；自动识别以标签说明；没有路线时首屏用数据布局 |
| 力量训练 | 主题、实际时长与已完成组数 | 动作分组、实际重量×次数、组间记录；计划组和实际组明确区分；继续训练只对可恢复会话出现 |
| 每日活动 | 步数、活跃时长、活动热量 | 自设目标进度；有小时数据才画小时分布；全天汇总与运动消耗不再次相加 |
| 感受和习惯 | 实际填写的心情、能量或次数 | 轻量日历、备注及发生时段；“未记录”和“明确未完成”不同；不生成综合健康分 |
| 一餐 | 餐次和食物名称；有照片用真实照片 | 逐食物份量与可编辑条目，营养横条与覆盖说明；缺项只显示已知部分，付款通过关联入口打开 |
| 食谱及食品批次 | 食谱成品／食材清单，或批次数量和到期日期 | 步骤式烹饪、份数换算；库存按批次与存放位置展开，采购不代表食用 |
| 消费及退款 | 大号金额、币种、商户与日期 | 小票式商品行；支出、退款与实付关系链；无商品明细时简化；不能跨币种直接求和 |
| 预算及周期事项 | 本期实际金额与预算／下次日期 | 使用进度与周期日历；未知金额保留未知，标记处理不自动生成付款 |
| 旅程 | 标题、日期、真实地点预览 | 按日行程轴、当天住宿和票券；预订为票券布局；住宿按入住退房跨度显示；保留离线入口 |
| 地点及停留 | 地点名、停留时间、地图 | 到访与相关材料；无有效定位则仅时间和地名，不画假路线 |
| 图片及截图 | 原图预览 | OCR 正文与已提取字段分区；来源页、相关事实和保存状态；Losna 长分析不占详情主体 |
| 网页及长文 | 标题、站点和正文 | 阅读排版、目录、原链接与固定原件；保留原文和整理内容的区别 |
| 文件及票券 | 文件预览或文件类型、票券关键日期 | 查看／导出原件；可检索内容和识别字段分区，失败不阻塞原件 |
| 录音及转写 | 播放器与时长 | 实际波形可后补，无波形先用播放进度；按时间定位转写段、纠错；不生成假波形 |
| 应用使用及采集活动 | 应用名、有效区间和时长 | 时间段列表、原文／截图证据、关联项目；未覆盖时段不计为零使用 |
| 物品及消耗品 | 名称、可选照片、位置及状态 | 购买／启用／维护时间线；保修、库存与补给独立分区 |
| 项目及目标 | 当前目标与下一项行动 | 里程碑、行动列表与证据；进度使用实际完成口径；历史回顾显示已有事实与证据 |

### 三个关键详情

**称重**：首屏绿色主题卡显示 68.4 kg、测量时间与设备，再展示体脂率、肌肉量、体水分比例。点击任一指标，切换到该指标的历史趋势和来源说明。变化使用同来源、同指标、同单位、适用算法一致的前次数据；缺基准时不显示箭头。体重下降只说明变化，不默认代表变好。体成分计算值使用“计算”标签，原始阻抗与公式版本留在来源区。

**一餐**：照片是可选内容，未拍照时直接用餐次标题与食物列表。每个食物一行，数量／单位清晰，编辑入口贴近食物。营养区写“已知部分 520 kcal · 2/3 项热量已知”，不能将它写成整餐总量或全天完成度。只有完整可用字段才画占比。消费记录以关联卡呈现，避免误认为外卖订单已经吃下。

**睡眠**：淡紫主卡包含时长和跨日开始结束。阶段图横轴是真实时间，无法提供分期时间时用阶段构成条并写明范围。可点击阶段查看该段时间，但不显示虚构睡眠分数。主睡眠与其他睡眠保留已有定义，不把重叠区间直接累加。

## 明快的视觉体系

默认预览与重点验收采用暗黑模式：页面背景 `#000000`，按用户指定的 Grok 式纯黑观感设计。主体内容直接排在黑底上，必要的可交互容器使用 `#101012`，不再逐层堆叠灰卡。浅色模式使用“奶油白底＋领域彩色主卡＋白色内容区”。每屏一个视觉主角；大面积中性灰改成留白和轻色块。饱和色用于主数字背板、图表和主要操作，小图标不承担整屏唯一的颜色。

| 用途 | 浅色模式色值 | 使用位置 |
| --- | --- | --- |
| 页面／正文 | `#FFF9F1` / `#212A31` | 暖白底，深色正文；次级正文 `#58636B` |
| 健康 | `#B9EF68` / `#173F2B` | 称重与身体主卡，保留健康绿色 |
| 饮食 | `#FFD39C` / `#683B16` | 餐次、食物与营养模块 |
| 睡眠 | `#DCD1FF` / `#47346F` | 睡眠主卡和分期身份色 |
| 活动与训练 | `#FFBFAE` / `#67302C` | 实际运动、动作和进度 |
| 消费 | `#FFE586` / `#59451A` | 金额和预算；退款另用文字与方向标记 |
| 旅行 | `#AEE7F3` / `#194A5B` | 行程、票券和地点 |
| 资料 | `#F7C5E3` / `#66354F` | 图片、网页和笔记 |
| 计划与物品 | `#C9D6FF` / `#31426B` | 任务、库存和物品档案 |

以上为设计候选 token，实施需检验实际文本对比度。领域颜色不等于健康判定，既有偏低／达标／偏高语义色仅用于有依据的状态徽标，并带文字。暗色模式背景固定 `#000000`，正文 `#F5F5F7`、次级正文 `#A8A8B0`、必要分隔 `#27272B`。彩色主卡沿用表中的亮色底与深色字，黑底上的普通指标采用亮色文字或局部色条；一屏至多一个大面积彩色主卡，其余用留白建立层级。提供可选降低彩色面积的紧凑布局，不改变纯黑基底。保留现有深色默认和已选外观，不强制重置；动态系统色不覆盖领域色映射。

- 大数字约 36–44 sp，标题 22–28 sp，正文 15–16 sp，说明不低于 12 sp；单位紧邻数值。
- 页面横边距 20 dp，主要块间距 20–24 dp，内容卡圆角 24 dp，轻量行不重复套卡。
- 使用一致的矢量图标，替换详情头部的字符占位符；原图保持原色，不用装饰插画替代内容。
- 按类型使用趋势、时间轴、地图、票券、食物清单和阅读正文；不为每页凑同样数量的卡片。
- 切换指标和展开内容使用短过渡，遵守减少动画设置；不做持续闪动、循环庆祝或把失败包装成彩色成功。
- 大字体与 320 dp 窄屏下指标网格转单列，按钮至少 48 dp 可触；图表提供文字摘要，不能只靠颜色。

Life 展示事实、趋势、原件和操作结果；本方案不增加“等待 Losna 分析”“批准处理”等中间页，不把 QQ 长分析复制成所有详情的默认模块。

## 实现接口与兼容

拟给 `life.timeline` 与 `life.search` 增加可选 `view: events | facts`，旧调用默认保留 facts，新界面显式用 events。新增类型化事件摘要包含稳定 `event_id`、`event_kind`、发生时间／日期及精度、主指标、辅助指标、成员数量、来源、完整性、匹配子项和可导航引用。返回独立事件计数，不改变旧 facts 计数含义。

新增只读事件详情能力建议命名 `life.get_event`，经共同 QueryService 与 Executor 授权路径读取，不新增写入成功路径。健康事件携带成员事实 ID 与版本，已有 `health.get_record` 保持兼容。新写入仍调用现有领域命令，编辑后的列表摘要由事实重算。

事件查询在服务端完成主体与成员可见性过滤、分组、搜索、排序及游标分页。游标绑定 view、过滤条件与 as-of 阅读边界，切换筛选重置游标。现有 as-of 若仅限制 created_at，不应宣称提供修订级历史快照；阅读中发生更正时沿用“有更新”提示和刷新后重新分页，不能悄悄变更排序造成漏项。

Android 增加 `EventSummary` 和按类型区分的详情展示模型；金额保留十进制与币种，时间保留精度，不先转成无类型字符串。组件拆为 BodyMeasurementDetail、SleepDetail、WorkoutDetail、MealDetail、MoneyDetail、LibraryDetail 等，公共 DetailScaffold 保留加载、错误、返回、更多和来源区。

Web 共享事件合同和术语，按类型分派组件；大屏允许正文与相关信息双栏，移动宽度单栏。通用字段渲染仅作未知类型后备，不能继续作为已支持类型的默认主体。

首期无需重写或删除原始健康数据。若核查发现旧记录缺少可靠归组证据，单独设计可回滚的关联补全，不能在客户端靠时间近似“去重”。

## 实施顺序与验收

1. **事件基础与称重**：健康分组、时间线和搜索合同、旧链接、称重列表与详情、核心色彩 token。先解决刷屏，不能先换颜色后仍显示几十项指标。
2. **高频详情**：睡眠、实际运动／力量训练、一餐、消费与图片资料；补齐真实数据预览和缺项状态。
3. **全局一致性**：首页与领域页、计划、库存物品、旅行票券、录音采集、其他表单和设置；Web 同源事件与分类详情跟进。

以上为设计时的实施顺序；当前完成类型、复用既有专属流程和验证范围以交付记录为准。

验收重点：

- 16 项同批称重只显示 1 次；跨页不拆组，第二次真实测量不被吞并；跨用户／设备无误合并。
- 迟到字段、重试、更正、删除、原始版本切换保持事件稳定；旧指标链接可定位，搜索子指标能找到父事件。
- 覆盖每种类型的有数据、缺字段、无数据、部分失败、离线缓存和无权限状态；不出现假零、假趋势、假地图或未授权的关联信息。
- 验证金额精度、营养覆盖、睡眠跨日、源值与计算值、单位与原字段差异；可视化不改变原有统计口径。
- 浅色／暗色、320／390 dp、200% 字体、屏幕阅读器与返回滚动恢复；长标题和复杂来源不能截断主要值。
- 合同生成、跨端回归、数据库分组分页测试、Android 编译与适用组件测试、Web 窄屏验收；视觉用合成样例，设备验收另列。

设计预览只使用合成数据；部署、签名和真实运行验证记录于独立交付与运维回执。
