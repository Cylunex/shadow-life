# 消费与商品统计口径

## 目标与入口

`life.consumption_stats` 是订单、商品与实际饮食的只读聚合能力。HTTP 入口为
`GET /api/life/consumption-stats`，Web「记录 → 统计」和 Android 饮食工作台右上角「统计」
使用同一合同。Agent 也通过能力注册表调用同一查询，不维护第二套计算逻辑。

查询显式接收 `from_on`、`to_on_exclusive` 和 IANA `time_zone`；客户端提供 1、3、6、12 个
自然月快捷范围，并把当前自然月计入范围。`to_on_exclusive` 是下一月首日，避免日期边界含糊。

## 统计事实与去重

- 仅纳入 `consumption_records.state = confirmed` 的购买，以及 `meals.state = active`、
  `intake_items.effective = true` 的饮食事实；草稿和作废记录不进入结果。
- 订单数按 `purchase.id` 去重，实际食用次数按 `meal.id` 去重。购买行、饮食行和退款先在
  各自的相关子查询聚合，再交给 kernel，避免多表连接导致笛卡尔放大。
- 退款按退款记录 ID 去重并归属原订单月份。它只减少净消费金额，不删除订单次数、购买次数
  或已经确认的食用次数。
- 金额使用六位定点十进制累加，并始终按币种分组；不做隐式汇率换算。缺少
  `money.entry.read` 时不返回金额，也不会把未知金额显示为零。金额排行要求该权限。
- 商品购买数量与实际食用数量分开；只在同一规范商品、同一口径、同一兼容单位内相加。
  `kg/g`、`L/ml` 会转换到共同单位，其余不同单位不会硬合并。

## 规范化与分类

当前算法版本为 `consumption-stats-v1`。规范化依次进行 Unicode NFKC、空白折叠和有限标点
折叠，因此全角/半角括号等差异可合并。用户维护的 `personal_aliases` 对商家和食物名称拥有
最高的名称映射优先级；结果同时返回原始名称和采用过的规范化步骤，便于追溯。

消费场景优先级为：显式业务分类 → 已确认餐次关联 → 维护规则 → 原始 scene → unknown。
`delivery` 本身不等于餐饮外卖；只有餐次关联或商家/品类等可靠信号存在时才归到餐饮外卖，
商超到家保持独立。

商品品类优先级为：显式 `category_key` → 维护规则 → unknown。规则只使用有限且带边界的稳定
关键词。服务费、包装费、餐具、规格/偏好说明、加料等行在参与排行前单独识别并排除，不能
用“包含某个常见字”的宽泛规则过滤真实商品。未命中的行保留在 unknown，不强行归类。

结果中的 `scope_source`、`category_source`、`normalization`、`coverage` 和 `unknowns` 共同构成
解释面：UI 必须展示覆盖率，低覆盖时必须能看到最小待识别清单。排行和趋势遵循场景/品类
筛选；覆盖率与待识别项始终描述完整时间窗，避免筛选把数据质量问题隐藏掉。

## 历史数据、上线与回滚

此版本不执行破坏性历史回填，也不新增持久化汇总表。查询始终读取现有不可变事实，在请求时
按版本化规则派生统计；因此上线无需数据库迁移，回滚只需回退应用版本，不会留下需要逆迁移
的衍生行。现有索引与主体隔离条件继续生效。

未来若规则需要重分类，应新增算法版本并用隔离数据库对固定事实集双跑，比较订单数、金额、
unknown 清单和覆盖率。只有在产品明确需要快照或性能要求时才引入物化汇总；届时必须同时提供
幂等回填作业、来源事实水位、算法版本、审计差异和独立回滚方案，不能原地覆盖原始订单或饮食
记录。

## 验证范围

kernel 回归覆盖名称变体、个人别名、服务行排除、餐饮/商超/未知外送、混合单位、权限覆盖、
退款、多币种、时区边界和空数据。PostgreSQL 回归通过真实命令写入订单、餐次、关联和退款，
验证数据库查询不会因连接关系重复计数。Web 与 Android 各自覆盖自然月范围计算。
