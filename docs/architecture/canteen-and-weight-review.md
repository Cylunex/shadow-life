# 食堂午餐与早晚称重

2026-11-19 · 已实现日结、周报、菜品档案和单餐复盘。Web 和 Android 共用 Life 的统计接口，Losna 使用同一份结果。食堂菜品可按档口区分，并保留别名、做法、分类和常用份量依据。餐盘和数值示例为合成样例。

## 从现有能力起步

- 门店菜单已有稳定食品 ID、门店归属、来源和带生效期的档口价目。一餐可关联实吃条目、原图和既有消费，每项可保留估算依据、净重与食用比例。[门店与摄入合同](../../shared/contracts/src/schemas.ts)
- 联合复盘已有热量、蛋白质、脂肪、碳水、纤维和钠的已知合计、估算数及覆盖天数。它每天选最后一次有效公斤读数。用户早晚都称时，做晨重趋势需要回到带时刻和来源的测量。三星的活动与主睡眠可从健康日汇总取。[联合复盘](wellness-review.md) · [健康指标显示口径](health-display-semantics.md)
- `life.diet_review` 返回单日和周期统计；`life.meal_diet_review` 按餐次 ID 返回实吃营养、有效份量、估算依据和来源修订。两者经 HTTP 和 skill CLI 提供，旧联合复盘继续用它已有的合同。[Life 接入约定](../agents/integration.md)

旧 Shadow Health 的趋势函数按两次测量间隔平滑体重，可用于三十天视图。旧版的摄入均值会纳入只记过一餐的日期，且在缺少目标时预设减重速率，本设计只借鉴平滑方法。日记与目标趋势的并排展示可参考开源 OpenNutriTracker；首批先把同一份统计交给聊天与现有复盘入口。[旧版实现（同级仓库）](../../../shadow-health/app/services/energy.py) · [OpenNutriTracker](https://github.com/simonoppowa/OpenNutriTracker)

## 菜品与门店

Android 从饮食进入独立的「菜品与门店」页面。门店页查询原有食品 ID、常用份量、档口价目和收录依据，也可用一道已收录的菜记餐。外卖门店和菜名从已确认的餐饮外卖订单和已识别的订单截图读取，排除包装、配送与餐具等行，原订单仍可打开核对。点过的菜可收录到同一门店菜单，原订单提供菜名依据。

「常吃」使用近 30 个当地日期内的有效实吃条目，按餐次去重。门店优先采用菜品记录里的门店，有唯一已确认的关联采购时可用于归属。同一餐同一道菜出现多行只算一餐，食用比例为 0 的条目和只下单的外卖不增加实吃次数。Android 单餐页显示实吃营养覆盖、份量和餐照，每个食物可以点开记录依据。

## 一份菜单可以用很多天，每份餐盘只属于一顿

| 信息归属 | 保存和复用的内容 | 更正后的行为 |
| --- | --- | --- |
| 门店菜品 | 稳定食品 ID、常用名、别名和出处。逐步补档口、做法、食物类别、常用量具及适用的营养基准，例如「这家档口一平勺的熟菜」。没有可靠克重时保留「一平勺」。 | 本人认出的新菜或菜单原件可积累为菜品；重复见到追加新出处。同名且做法不同的档口菜可分别识别。标签和份量基准留来源、适用范围和修订。 |
| 当天餐盘 | 餐次 ID、门店／档口、原图或口述、菜品 ID 或待识别文字、本次取量、实吃比例、每项营养和取值依据。菜单上可选、夹到盘中和实际吃下是三种信息。 | 「这道剩一半」只修订这一行。「那是烧豆腐」修订本餐匹配；有菜单维护委托时复用或补充有出处的菜名。明确零份保留原记录，摄入和食物组出现次数均排除它。 |
| 档口计价 | 价格按门店、档口、日期和计费方式查。可记录单价、重量单位、固定费用及价目出处。 | 新价格从生效日使用。过去的菜谱、每份营养和实吃记录保留当时版本；如需修正具体餐次，定位原记录再更正并重算相关复盘。 |

识别时先分页查常去门店，优先匹配本人纠正过的菜名，再看当餐原话、菜单或餐照。跨档口重名且无法区分时保留本餐描述，餐照足以看出是蔬菜时仍可分析搭配。积累顺序是**菜名 → 食物类别和做法 → 常用份量 → 有依据的营养基准**。同一道菜多次出现在照片里，能提高身份匹配把握；多次目测的份量仍标为估算。已有餐次的营养不因菜单新增一个平均值而自动回填。

### 自选菜与称重档口

| 午餐情形 | 能算到哪一步 | Losna 可以怎样解释 |
| --- | --- | --- |
| 自选多道、只知道菜名或有餐照 | 识别同盘的主食、蔬菜、蛋白质来源和混合菜。已知「半碗、几勺」可直接描述。具备适用的量具或熟食基准才换算；仅凭照片给出的估算要随结果显示。 | 白饭、杂粮饭再加一小段玉米，先看合起来占几格或几碗。三样各尝一口和三样各拿一份，应给不同判断。重量相同的不同主食也可能含有不同碳水。 |
| 单一称重档口，如麻辣烫 | 有小票净重时取净重；否则核对当日有效价目、计价范围、固定费、优惠和分单。可归属的称重金额 ÷ 单价 × 计价克数得到该部分估重。固定价主食、单点饮料等单列。 | 整盘估重与盘内分配分别标注。口述能确认几块豆腐，可保留个数；能分配给各项的克数之和不得超过整盘。无法归属的重量留作余量，汤底、实际喝汤量和钠各自保留未知。 |
| 多图、混合档口或价目冲突 | 同一盘多角度合并到同一餐。有共同称重范围才分配总重；冲突时仍返回实吃菜名、已知数量及来源。 | 一张付款和两张照片仍是一顿。菜数超过单次识别工具容量时保留全部原条目和未分配部分，不能把同一个整盘总重按两批各分一次。 |

总量和营养均以实吃为准。本餐营养已按原份量保存时，每项只乘一次 `consumed_fraction`。门店基准须先对齐可食部分、生熟状态和单位，再按本次份量折算。混合菜可标记含蔬菜和豆制品；只有配方与分量明确时才拆克数。一天多次吃到同组食物，在「出现天数」里只计一天。食物类别频率、可比份量和营养素数值各自提供分母。

归纳午餐习惯时，分母取窗口内已确认的该门店午餐，标出其中能辨认食物类别、能比较份量的各有几顿。同餐同组去重。遇到部分菜名未知时，表述为「六顿已记录午餐中，至少四顿有蔬菜，两顿资料不全」。需要判断某类吃得多或少时，进一步比较本人同档口、同计量方式的实吃份量；只有种类数相似的两盘仍可相差很大。

## 判断「多、少、缺什么」

七天概览先列**蔬菜、水果、奶类、豆类、全谷物**各有几天确认吃过；午餐习惯另列同店已记录餐数。早餐的牛奶可计入当天奶类，不能算到食堂午餐；同一天两餐吃豆腐仍算一个豆类日。只记午餐的日子也能作为「已吃过」的证据，报告同时给出缺餐或无法分类的天数。单餐与周期可以展示钙、铁的已知摄入和覆盖。用标签或匹配生熟状态、可食部和份量的成分资料标注出处。[中国食物营养成分查询平台](https://nlc.chinanutri.cn/fq/)

| 用户问题 | 最低依据 | 返回的判断 |
| --- | --- | --- |
| 这顿搭配怎样？ | 已确认食用的条目、可辨认的类别、门店在售或历史菜单的出处 | 优先说一件能在同一档口做到的事。份量未知时说看见哪些搭配；有可比份量时才说某一类占得较多。历史菜单建议加上「如果今天有」。 |
| 今天吃多了？ | 有明确且仍适用的个人摄入上沿。可靠的已知摄入小计已经越过上沿，其他食物尚未记完也可判断。 | 标明「已记录部分」和比较对象；超出主要依赖目测、且估量误差可能改变方向时，报告大致范围或「还看不准」。不从单日秤重或手表耗能推导上沿。 |
| 今天吃少了？ | 本地日已结束或本人明确当天进食已结束；本人表示基本记全；主要餐食有可比份量，目标字段覆盖足以判断，且有适用目标下沿。 | 条件都满足才说「这一天低于你的目标」。一餐的蛋白质来源少，可以对这一餐给搭配建议。全天完整性未知时仅展示已知摄入。 |
| 最近常缺哪类食物？ | 最近七天或多周的实吃记录，按食物组给可判断的餐数、天数和未知项。要比较营养素，还需有对应字段、可比的全天记录和适用人群的参考范围。 | 可以说「在能辨认的五顿午餐里，只有一顿出现豆制品」。纤维、钠、钙或铁字段稀疏时回到可见食物来源。膳食摄入观察只能支持饮食建议，生理缺乏需要其他证据。[中国居民膳食指南](https://dg.cnsoc.org/article/04/J4-AsD_DR3OLQMnHG0-jZA.html) · [营养素参考摄入量](https://www.cnsoc.org/drpostand/) |

按本人、本地日期和时区保存可更正的饮食记录状态，区分「本人表示基本记全」「明确还有漏记」「未知」。允许用一句「今天都记全了」设置，旧日期默认未知。增加、撤销餐食时实时更新字段覆盖；日期移走、记录撤销等使完整性声明失去依据时标为待重新核对。餐数、照片数、字段齐全和当天结束都不能单独产生完整性声明。[Cronometer 的完整日筛选](https://support.cronometer.com/hc/en-us/articles/360018569691-Nutrition-Report)

## 早晚称重与三星健康

1. **晨重和晚重各自成序列。** 先按本人选用的秤、单位、有效修订和测量当地时刻归组。首版默认晨间 05:00–11:00（不含 11:00），晚间 18:00–次日 03:00（不含 03:00），时段可按作息调整。跨午夜的晚测在趋势里归前一晚，原测量日期保留。窗口内同一秤晨取首次、晚取末次；其他点仍可在明细查看。缺时刻、自动补值和来源不明不进分时段比较。三星同步副本不能增加秤的样本数；缺少同源证据时各来源分开展示。
2. **周报先列可比样本数，再说方向。** 对照相邻两个七天窗口的晨重均值，保留各自测量天数、范围和具体日期。首版建议两个窗口各至少三个不同晨测日才展示均值差，这是展示门槛。取样集中、波动范围重叠较大或差异很小时只报观察值。连续三至四周同向、饮食有覆盖且本人有相应目标时，才提出一个份量调整供尝试。行动后再查看接下来两到三周的同条件数据。腰围目标有实际腰围时优先单列该趋势，缺测时只讨论体重本身。[MacroFactor 的摄入与体重趋势方法](https://help.macrofactorapp.com/en/articles/26-how-should-i-interpret-changes-to-my-energy-expenditure)
3. **体脂秤的其他指标跟随同一次测量。** 体脂率、肌肉量、体水分率按来源、算法版本（可得时）、单位和晨晚时段分别比较。同一读数的公斤、百分比与内脏脂肪等级分栏展示，各自统计有效天数。设备估值受测量条件影响，单次或早晚差值只作为观察；无法匹配同次测量的字段留空。换秤或算法切换时标断点。[小米 S400 测量说明](https://www.mi.com/uk/support/faq/details/KA-107891/)
4. **三星只解释背景。** 从 `health.daily` 取服务端已归并的步数、活动分钟和按醒来日归属的主睡眠。周报按有效天数给步数中位数，主睡眠给有记录的晚数与时长。零步、缺测、当天尚未同步分别表达；低步数本身不能判断佩戴时间。设备活动热量、运动会话热量沿用日汇总来源，不能相加或直接换算成一顿可吃多少。本人近期只想调整吃饭时，优先使用午餐建议。

## 交付与验收

沿用 Losna 日结和周报。Life Web 和 Android 的饮食入口可查门店档案与实吃详情。两端复盘读取同秤晨晚数据，Web 可保存称重时段和设备选择。菜品档案在记录摄入时保存来源版本和类别快照，菜品后续的份量或营养修改不会重新计算已保存的餐次。

| 顺序 | 工程交付 | 合成场景与预期 |
| --- | --- | --- |
| 1 · 已有日结与周报 | 复用现有联合复盘、按需读取的餐次明细、菜单与有效目标。先交付有来源的下一餐建议和已有证据能支持的趋势观察。 | 只有午餐且两道菜缺份量时，日结能从门店菜给一个具体选项，保留全天摄入未知。只拿到旧查询的每日末次体重时，按该口径报告或省略晨重比较。 |
| 2 · 单日与周期 | 新查询按当地日期支持单日、近 7 天和近 30 天。单日返回各项已知合计、日完整状态、目标及可判断方向；多日另给各食物组的餐数与天数、逐项营养覆盖、晨晚序列、对应前期与三星背景。分别复用餐食、健康、意图的读取权限。每条判断附比较依据、期间、来源引用、修订和计算时点。 | 仅记午餐时仍有搭配建议，全天能量判为未知。前一天 23:50 和次日 00:10 同属一个晚间窗口；晨测缺一天保持空。三星再上传一份同晨体重后晨重均值不变。七天只有三晚有睡眠时，结果明确是三晚。 |
| 3 · 午餐详情与跨端回归 | 新查询支持单个餐次 ID，返回实吃条目、类别、可比份量、估算依据与来源修订。Losna 通过 Life skill 读取；旧服务沿用第一阶段。餐次或秤读数更正后重新读取。 | 一盘两图仍是一餐，半份只折算一次，零份保留菜单身份。固定价饮料排除在称重菜之外。重复询问时复用已有菜品，无健康读取权仍可解释本人可读午餐。新合同完整生成并做 Kernel、数据库、HTTP、CLI、Web／Android 兼容与 Losna 离线回归。 |

优先验收「下一顿怎么吃」与「体重走势和我的目标合不合」。个体能量消耗反推和自动热量调整需要更长时间的可比记录及单独验证，留在后续设计。日结去重、当餐纠正与每周行动的对话示例见同级仓库的 [Losna 健康跟进设计](../../../shadow-losna/docs/life-health-followup.md)。
