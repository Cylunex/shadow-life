# Travel 与业务详情交互优化

本轮以 Android 原生交互为主，同时统一网页的按天浏览、记录关联和详情展示。
交互参考 [Wanderlog 的行程规划](https://wanderlog.com/plan-a-trip) 与
[日程地图](https://wanderlog.com/travel-maps)：先选择旅程和日期，再查看或调整当天安排。

## Travel

- Android 默认加载当前或即将开始的旅程，支持切换旅程、日期，以及新增、修改、排序和移除当天点位。
- 行程按日期分页；每个点位独立展示时间、地点和备注。空白日期仍可安排；修改旅程日期后，已有的范围外日程仍可访问。
- 原生详情复用当天行程展示，预订、实际交通和到访分别展示。预订付款可进入关联账目。
- 网页默认展示日程，地图可查看当天地点或全部地点；辅助操作折叠，编辑表单直接替换当前日程区域。
- 时间使用旅程时区。Android 保留未改动的原始时间戳，对新增的无效或夏令时歧义时间提示修正。
- 保存沿用统一 Executor 和 Android 队列；修改携带当前日计划版本，点位保留稳定身份。
- 点位中的实际到访操作携带旅程关联；计划和到访仍是不同业务事实。

## 关联与详情

- 修复 Android 消费详情仅请求金额、导致关联餐次和购买明细被客户端隐藏的问题。
- 补齐独立餐次付款的反向查询，以及餐次到消费、退款到原交易、原交易到退款、旅费到旅程的明确关联。
- 关联查询校验主体、业务读权限与当前旅程访问权；没有消费权限时不返回预订付款入口。
- 健康详情支持进入同一次测量的其他指标；物品维护事件支持进入费用与凭证。
- 营养按食物、预订按对象展示。长列表分段展开，来源和历史默认折叠，关联记录可以直接打开。
- 网页详情直接展示核心信息，合并基础字段，保留金额精度并清理营养数值的小数尾零。
- 修复浏览器原生 fetch 被作为控制器成员调用时的接收者错误，避免保存被误报为网络中断。
