# 花有谱付款采集参考审查

审查日期：2026-11-05。参考 [AldenHe/huayoupu-ledger](https://github.com/AldenHe/huayoupu-ledger)，固定提交 `abb796d829748403612f09e89909819b974565c7`。同时阅读其 [参考实现说明](https://github.com/AldenHe/huayoupu-ledger/blob/abb796d829748403612f09e89909819b974565c7/.github/REFERENCE.md)，核对支付页检测、访问生命周期、采集目标、识别队列、节点读取、去重与相关测试。

## 对照结果

| 能力 | Life 的处理 |
| --- | --- |
| 付款成功后自动触发 | 新增独立的“付款后自动识别”开关，按当前 Life 账号、来源应用、支付平台和平台账号保存；不依赖摇一摇或普通屏幕持续采集开关 |
| 微信、支付宝原生结果页 | 校验来源包名、页面类型、成功状态、完成按钮和唯一实付金额；排除详情、历史、聊天、收入、退款、待付款、认证页面 |
| 第三方 App 支付 | 跳转支付应用时按支付应用规则读取；留在商户 App 时需单独启用该来源，并匹配实际支付平台、成功状态、完成按钮和标注的实付金额。不宣称支持全部 SDK 或全部版本 |
| 页面事件过密、页面尚未加载 | 同一窗口合并事件；一次读取过程最多四轮延迟重读。节点读取在独立单线程执行，单次等待最多 650ms，超时后不积压并行任务，不使用迟到结果 |
| 深层文字、内容描述 | 同时读取 text 和 contentDescription；检查完整节点树。节点、深度、长度有界，遇认证输入、敏感节点或截断树不采集 |
| 访问去重和再次进入页面 | 账号范围内保存有限数量的已提交指纹；完整交易优先使用平台交易身份，不完整帧可由后续完整帧补充。服务端继续按平台、账号和交易身份去重 |
| 跨应用去重 | 采集保存实际支付平台及账号，商户 App 的微信结果与随后微信详情、文件账单导入沿用同一账目身份 |
| 离线队列与运行状态 | 复用 Life 现有账号绑定加密队列；增加服务状态、近期读取结果、无障碍与后台限制入口；锁屏、账号变化、关闭开关及离开目标窗口使旧读取失效 |
| 不完整成功页 | 缺交易号、明确付款时间、人民币证据或有字段冲突时只保存材料，不以当前时间、同金额或随机身份生成消费；可通过账单详情摇一摇补录 |
| 导出恢复 | 支付来源上下文随材料导出和恢复，恢复不触发消费写入；删除材料时清除上下文 |

## 保留 Life 现有实现的部分

支付成功页筛选只是采集条件。最终付款解释仍由 kernel 完成，经共同 Executor、既有账单导入与消费账本写入；不增加第二套账本。金额、币种、身份、权限、冲突和 Ledger 迁移围栏继续生效。退款不由成功页金额推算，消费与购买、餐次、退款关系仍沿用已有模型。

参考项目自身是针对特定支付页面的适配，不能把它的功能描述理解为对任意第三方 SDK 的全覆盖承诺。Life 本次没有自动截图、自动点进账单详情或读取支付密码；既有主动截图与 OCR 流程继续保留。

参考项目中的第三方组件类名兼容手段、嵌入式 OCR 模型及商家图标提取未引入。前者依赖应用版本的特殊行为，后两者涉及额外模型、资源与真机性能验证，现有采集和资料处理已能承担对应基础功能。

参考仓库为 GPL-3.0。本次按功能行为独立实现，未复制其源码、模型、图片或运行库。

## 合同与验证边界

新增可选 `payment_context`（支付平台、平台账号、`payment_success` 触发来源），持久化迁移为 `0054_payment_capture_context.sql`。普通上传不能单独附加该上下文来隐式要求记账；必须带显式 `record_expenses` 并通过相应写权限。归档恢复只保留来源上下文，不能携带记账意图。

回归覆盖原生和商户结果筛选、账号隔离、反复窗口事件、深层节点、敏感与不完整树、成功页缺字段、跨来源去重、权限、币种与备份恢复。实际微信／支付宝版本、商户 SDK 页面和系统后台存活仍需安装后真机验证，本轮未部署服务、构建 APK 或安装到手机。
