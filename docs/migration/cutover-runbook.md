# Health / Ledger cutover runbook

1. Restore the latest backups into isolation and verify they can be queried. Export both legacy databases with the read-only exporter and hash every referenced asset. Retain the generated snapshot content ID, catalog fingerprint, per-table hashes and exact schema metadata.
2. Generate and complete a mapping review for each snapshot. `mapping audit` must report both complete coverage and ready: every discovered table and column has an explicit disposition, included active facts are not excluded, and the review is bound to the exact snapshot. Map each legacy owner to one verified Life subject. Validate the resulting bundle and verify every manifest entry against the actual file bytes, rejecting absolute paths, directory escapes, missing files, size differences and hash differences. Resolve all unsupported fields and inaccessible assets.
3. Migrate an empty isolated Life database to the bundle's exact target schema and run `restore-drill` with its explicit isolation guard. It must refuse a non-empty database, apply every component once, replay every component without a second write, and reconcile from fresh target readback. Archive the snapshot, mapping audit, bundle and drill report together.
4. Run reconciliation. All source objects need a disposition; every planned source-to-target mapping must exist exactly once in both directions; all target components, child collections, links, exact per-currency money totals, raw health revisions, nutritional snapshots and source hashes must match. Evidence hashes must be built from fresh target readback and verified file facts, never from the expected bundle. Complete every projection checkpoint.
5. Put Life Health and Ledger into `read_only`, stop old web/API/MCP writers, scheduled jobs, directory ingestion and device sync, then drain or quarantine old offline queues. Take the final consistent snapshots and apply the `final-delta` bundle. Each changed target is updated only if its last applied readback hash still matches; otherwise the batch records a conflict. Deletions require an advancing source revision and become domain tombstones with retained revision history rather than destructive row removal.
6. Run `cutover-check` against the exact final snapshot bundle. It selects the matching `final_delta` batch, requires both Life write epochs to remain `read_only`, verifies all normalization and daily-projection queues are drained, and reruns target reconciliation inside one repeatable-read transaction. A prior successful summary is never sufficient. Change each `write_epochs` row to the next epoch and `life` only after this fresh report is ready. Route supported clients to Life. Clients read `/api/write-epochs` and send the values as `x-shadow-write-epochs: health=N,ledger=N`; a stale supplied epoch is rejected inside the same transaction as the write. The server-side stage remains authoritative when older clients do not supply an epoch.
7. Verify Web, MCP, Agent and Android reads and writes, including an unknown response replay, cross-day payment, cross-month refund, Health cursor replay and an attachment reference. Keep old databases read-only and take a new Life backup.
8. Revoke legacy machine credentials and retire the old services only after the observation window and restore exercise succeed.

Before Life accepts a new write, rollback may reopen the verified final legacy state as the sole writer. After Life accepts a new write, freeze Life and repair forward unless a separately tested reverse mapper can preserve every new fact, receipt and asset reference. Never reopen both writers.
